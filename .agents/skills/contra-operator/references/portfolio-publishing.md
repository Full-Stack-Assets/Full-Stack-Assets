# Portfolio, Services, and Products

## Evidence intake

Before creating public Contra content, classify every externally checkable claim:
- `VERIFIED_RUNTIME`: observed from the live product/runtime/database.
- `VERIFIED_REPOSITORY`: verified from the current repository/tests/build artifacts.
- `VERIFIED_DOCUMENT`: supported by a supplied first-party document or artifact.
- `SYNTHETIC_DEMO`: illustrative only and visibly labeled demo/synthetic.
- `UNVERIFIED`: omit from public copy.

Never invent metrics, customer names, revenue, conversion rates, integration state, deployment status, or website/Contra URLs. A generated dashboard with realistic numbers is not evidence.

## Publishing workflow

1. Read the existing Contra profile/work to avoid duplicates.
2. Verify title, description, skills/tags, role, project link, and each image source.
3. Prefer an actual product screenshot. If unavailable, use an accurate branded concept visual with a visible concept/demo label.
4. Create or prepare the Work/service/product as a draft when the current toolset supports it.
5. In tiered mode, present the material public changes and obtain approval before publish.
6. Preserve any Contra-native prepare/confirm gate even in maximum mode.
7. After publish, read the resource back. Report the canonical Contra URL returned by Contra; never manufacture a slug.
8. If the returned content differs materially from the approved draft, disclose the difference and correct it through the normal confirmation flow.
